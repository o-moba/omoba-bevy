## Before distributing a build

1. Record the exact source revision and any local changes used to build it.
   A local or unpublished commit is not a public source offer. A repository
   homepage by itself does not establish that matching source is available.
2. Make the source required by the applicable licenses available to recipients.
   For MPL client/library binaries this includes covered files and modifications.
   For AGPL binaries provide Corresponding Source as defined by the license,
   including required build/install material and covered dependencies; use a
   permitted delivery method under section 6. A source archive of this repository
   alone may be insufficient for a complete server build.
3. Give recipients clear instructions to obtain that exact source and keep the
   offer/access available for the period and on the terms your delivery method
   requires. Include license texts and preserve dependency/asset notices.
4. For a modified AGPL server accessible over a network, prominently offer all
   interacting users the Corresponding Source of the running version under
   section 13. Present the offer in the service's user-facing entry/client flow;
   a private log line or a link to an unrelated upstream revision is insufficient.
5. Verify the actual dependency licenses, avatar permissions and store/platform
   distribution terms. A packaging script does not provide missing permissions,
   obtain store approval or make a private source revision public.

Native and mobile packagers include the project legal notices. Their inclusion
is one part of compliance; it does not certify the completed source offer or all
third-party obligations. Build revision metadata identifies source locally, and
must not be presented as verified public availability.

Fork operators must substitute their actual source location and version when
appropriate. Source availability does not require publication of player data,
private signing keys or other secrets. Do not include them in source archives.
The standard license definitions govern which source materials are required.

For problems finding source for an official distributed build, report its build
identifier through the [project repository](https://github.com/o-moba/omoba-bevy).
For a separately operated service, contact that operator using its source offer.
