# Website class workshop and local game import

The website class workshop composes the game's **12 modular cores and 48 reusable
skills**. The creator asset gallery separately browses **17 classes and 68
abilities**; the twenty older class-owned abilities are not modular recipe IDs.
A saved build is a named recipe, not a new `HeroClass`, executable skill script
or permission to enter a public/ranked match.

## Shared document

`shared::workshop::ClassBuildDocument` is the strict import/persistence boundary:

```json
{
  "schema": "omoba.class-build.v1",
  "name": "Light and rockets",
  "description": "A local experiment with a borrowed ultimate.",
  "recipe": {
    "schema_version": 1,
    "catalog_revision": "standard-kits-6",
    "core": "dawnweaver",
    "passive": "radiance",
    "skills": ["dawn_bind", "dawn_barrier", "dawn_field", "wild_rocket"]
  }
}
```

The file is bounded to 8 KiB. Names have 1–80 Unicode characters, are nonblank and
contain no control characters; descriptions have at most 1000 Unicode characters.
Every field shown is required, and unknown fields are rejected. Account IDs,
appearance paths, credentials and numeric combat overrides are not document
fields. Invalid imports are reported without trimming or replacing their recipe.

`parse(&[u8])` applies the file limit, strict deserialization and validation.
`validate()` returns a `ResolvedLoadout` using the authoritative resolver.
`sandbox_config()` constructs a safe complete `SandboxConfig` from game defaults.
The Account API can deserialize a nested document and call the same `validate()`
before private storage; account ownership comes from its authenticated session.
Saving a build does not publish it or approve any asset.

## Rules and browser metadata

Four unique IDs occupy physical Q/W/E/R in array order. `wild_switch` needs a
Repeater attack profile (currently Wildspark). `orbital_field` and
`orbital_collapse` need `orbital_command` or `orbital_guard` in the same recipe.
`loadout::requirements()` supplies these capability constraints to both admission
and the workshop exporter. The core retains growth, basic attack and resource
policy. Original skill roles retain unlock levels 1/2/4/6 even when moved to a
different key. Four distinct ultimates are legal and remain locked until level 6.

The recipe supports twelve passive IDs. The first website interface keeps each
core's default passive; a valid imported passive is still part of the strict
recipe and must not be silently replaced. Avatar and handheld choice remain
separate. Borrowing a Wildspark skill does not equip its gun on another core.

Generate and verify the web snapshot with the existing shared build cache:

```sh
export CARGO_TARGET_DIR=/Users/wotori/git/ekza/omoba-bevy/target
python3 scripts/export_workshop.py
python3 scripts/export_workshop.py --check
cargo test --locked -p shared --lib
python3 -m unittest discover -s scripts -p test_combat_test.py
```

`shared/assets/catalog/workshop.json` is generated by compiled Rust definitions,
not an independently maintained web balance table. Its `omoba.workshop.v1`
schema includes presets, passives, skill costs/ranges/cooldowns, original unlock
levels, dependencies, protocol/catalogue versions, document limits and a complete
safe sandbox template. The Python wrapper records the newest commit touching
any consumed source path, hashes of all consumed shared sources and a content
revision using the same canonical JSON as
the asset catalogue. Snapshot-only and unrelated documentation commits do not
change this source revision or make `--check` perpetually stale. Uncommitted
changes are identified by input hashes. Re-export both snapshots after the final game commit when
preparing a website snapshot so their source provenance matches.

The underlying dependency-free Rust example can emit plain compiled metadata:

```sh
cargo run --locked -p shared --example export_workshop
```

## Play a downloaded build

The workshop has separate downloads for the named build document and a complete
local Combat Test preset. Import a document using the launcher adapter:

```sh
python3 scripts/combat_test.py --class-build "$HOME/Downloads/light-and-rockets.json"
```

This invokes the shared Rust parser before starting native processes, derives the
core, and makes a level-six actor with rank-one skills, normal resources and
cooldowns, class-default appearance and a training target. Input documents cannot
supply arbitrary actor statistics, cheat flags or service settings. Logs and
the generated native preset are written below the shared target cache, including
when the command runs from an isolated worktree.

With compatible prebuilt binaries, avoid rebuilding the native renderer:

```sh
python3 scripts/combat_test.py --class-build "$HOME/Downloads/light-and-rockets.json" \
  --bind 127.0.0.1:4049 \
  --client-binary "$CARGO_TARGET_DIR/debug/client" \
  --server-binary "$CARGO_TARGET_DIR/debug/server"
```

The separately downloaded complete preset uses the existing native path:

```sh
python3 scripts/combat_test.py --hero dawnweaver \
  --preset "$HOME/Downloads/light-and-rockets-combat-test.json"
```

Conversion without starting a match is useful for verification:

```sh
cargo run --locked -p shared --example export_workshop -- \
  --class-build "$HOME/Downloads/light-and-rockets.json" \
  --output /tmp/light-and-rockets-combat-test.json
```

The website creates the same safe preset by cloning `sandboxTemplate`, setting
`player.hero` and `player.recipe` from the validated recipe, and setting
`player.max_hp` to that core's `baseHp`. It must not merge arbitrary imported
document fields into the template. Source and protocol versions must match the
client/host used for a demonstration.

The existing client sends `ApplyConfig` and `ResetDuel`; the host validates the
whole configuration atomically and installs the resolved kit on the real actor.
Rejected configuration preserves the previous actor. Changes clear old skill
state and retain session identity. F6 toggles the development panel; close it to
use the regular combat controls against the target.

## Admission and proof boundary

This route is an explicit loopback development host, without ranked progress.
The launcher strips production service configuration from child environments.
Public Join/draft have no custom recipe field. The host's existing gates reject
authoring on public/allocated matches and require current protocol negotiation.
No identity data is needed in an executable recipe; OMOBA account ownership and
an optional Ekza library connection stay outside gameplay admission.

A successful JSON validation is not a gameplay demonstration. Record the actual
browser download, server acceptance and at least one native cast/target result
for the chosen mixed build. A browser preview shows its current core/skill
references; native proof establishes that the engine admitted and executed it.
