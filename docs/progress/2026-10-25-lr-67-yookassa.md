# 2026-10-25 — LR-67b: YooKassa provider in the Account API

## Goal

LR-67 (RU donations through YooKassa with tiered hero auras), part b: the
YooKassa provider flow in the Account API on top of LR-67a (tier engine, portal
schema 9, `settle_payment_tx` / `settle_refund_tx`, merged in PR #128): the
checkout, the owner's payment list, the public webhook, the reconciliation loop
with the refund scan, the 54-FZ receipt, the env and the RU host kit. Contract:
`docs/plans/launch-readiness.md` LR-67 (as amended), section 7 and its "Rules for
M0 items so they survive LR-68", ADR-024 and ADR-025. The rules are ported from
the owner's production YooKassa integration (vibe-piano `lib/billing/*`, read
only).

## What changed

- **`account-api/src/supporter/yookassa/`** (new submodules of `yookassa.rs`):
  - `api.rs`: the `/v3` REST client (Basic shop credentials, no SDK, no proxy, no
    redirects, 3 s connect / 5 s total): `POST /payments` with the stored
    Idempotence-Key, `GET /payments/{id}`, `GET /refunds/{id}`, paged
    `GET /refunds`. Replies are parsed to the fields settlement needs and checked
    (provider ids, RUB only, amounts as integer kopecks from `"1000.00"` strings,
    `paid` agreeing with the status, ISO times to epoch seconds without a date
    crate, HTTPS-only confirmation URLs without credentials). A failed call logs
    only its operation, the HTTP status and YooKassa's `x-request-id`.
  - `checkout.rs`: `POST /v1/me/supporter/yookassa/checkout`
    (`{amount_rub, receipt_email, quote, offer_version}` + `Idempotency-Key`) →
    `{confirmation_url, attempt_id}`. Amount: tiers or 100–100 000 ₽; the quote
    (`amount_minor`, `RUB`, 30 days, the tier the donation reaches) must equal the
    server's or `409 reload`. The attempt (keyed hash of profile + browser key),
    its Idempotence-Key and the frozen «Чеки от ЮKassa» receipt (e-mail, one
    `service` item, `full_payment`, `vat_code` from env, «OMOBA — поддержка проекта
    (аура на 30 дней)») commit first; the attempt is then claimed (`charging`,
    120 s lease) and only then posted. The same key repeats the attempt (re-read,
    never re-created); another amount/e-mail/offer with it is
    `409 idempotency_conflict`. Return URL `<OMOBA_PORTAL_ORIGIN>/supporter?paid=1`.
    New charges need `OMOBA_YOOKASSA_NEW_CHARGES=1` and a refund scan that
    succeeded in the last 30 minutes (`503 new_charges_paused`); at most 10 open
    attempts per profile and day. `GET /v1/me/supporter/yookassa/payments`: the
    owner's last 20 attempts of the year (`pending|succeeded|canceled|review`,
    `refunded_minor`), re-reading the newest submitted one of the last hour first.
    The dashboard gains a `yookassa` block (`available`, `new_charges`, prices).
  - `notifications.rs`: `POST /v1/supporter/yookassa/notifications` (public; per
    IP 120/min, 600/min in total). The body only names an object: unknown objects
    answer `200 ignored` with no API call; known ones are re-read and settled
    (`200 accepted`); processing errors answer 5xx.
  - `reconcile.rs`: the loop (every 60 s in `main.rs`, next to the Apple one):
    closes never-posted attempts after an hour; reserves 8 open attempts per pass
    (advisory lock `721946110`, oldest `last_polled_at` first) and re-reads,
    replays a lost create with the same key and body under 23 h, or moves it to
    manual review (`provider_replay_window_expired` + issue, never posted again);
    scans refunds in a fixed window with YooKassa's cursor stored after each page
    (2 × 32 per pass), queueing unsettleable refunds as issues before the cursor
    moves, restarting the window after a failed list, retrying pending/failed
    refund issues.
- **`yookassa.rs`**: `api_base` in `YooKassaConfig` (production
  `https://api.yookassa.ru/v3`; `OMOBA_YOOKASSA_TEST_API_ORIGIN`, a loopback
  `http://` origin, only in debug builds — a release build refuses to start with
  it). A payment bound to an attempt whose metadata names another attempt is not
  settled.
- **Migration 009 fix (unreleased).** Its refund-scan cursor CHECK used
  `^[!-~]{1,512}$`; PostgreSQL caps a regex repetition count at 255, so every
  non-null cursor write failed ("invalid repetition count(s)") — found by the new
  durable-cursor test. Now `cursor ~ '^[!-~]+$' AND length(cursor)<=512`. No RU
  database exists; a database that already applied the old 009 (disposable test
  databases; the global dev contour never writes this table) is fixed with:
  `ALTER TABLE portal.supporter_yookassa_refund_scan DROP CONSTRAINT supporter_yookassa_refund_scan_cursor_check, ADD CONSTRAINT supporter_yookassa_refund_scan_cursor_check CHECK(cursor ~ '^[!-~]+$' AND length(cursor)<=512);`
- **`lib.rs` / `main.rs`**: the three routes (provider routes stay 404 outside a
  YooKassa market), the new rate buckets, the loop.
- **RU kit**: `Caddyfile.ru` passes the webhook in its own public `@yookassa`
  handle (exact path, POST, `X-Real-IP` overwritten); `account-api.env.example`
  documents the four settings commented out (placeholders only);
  `ru_host.py` accepts them as optional and validates them like the API
  (all-or-none, numeric shop id, VAT 1–12, switch 0/1, no placeholder) and
  refuses the test origin on a host; README "YooKassa" runbook (shop settings,
  webhook URL and events, test shop, turning on, pausing, manual review with
  hand-made notifications).
- **Docs**: `account-api/README.md`, `account-api/docs/openapi.json` (three
  paths, `YooKassaQuote`, `YooKassaCheckout`, `YooKassaPayment`, dashboard
  `yookassa`), `docs/supporter.md` ("YooKassa donations"), `docs/markets.md`,
  `docs/features.md` (Hero tiers section), ADR-024 status,
  `docs/architecture/{system,protocols,identity-and-accounts,data}.md`, the
  LR-67 acceptance items for the Account API tests and the docs.

## Acceptance (LR-67, the parts in LR-67b)

- Account API Postgres tests against a loopback YooKassa stand-in — done
  (`account-api/tests/yookassa_provider_postgres.rs`): the key is committed and
  the attempt claimed before the POST (checked by the stand-in inside the POST);
  a lost create is replayed with the same key and body under 23 h (one payment),
  a crash after the claim too, and over 23 h it goes to manual review with no
  POST; webhooks for unknown ids make no API call; a forged "succeeded" body
  grants nothing; duplicate `succeeded` grants once; `canceled` after `succeeded`
  is ignored; a refund before its payment settles the payment first; partial and
  full refunds (webhook and scan) recompute the tier and revoke; the refund scan
  keeps a durable cursor and restarts its window after a failure; stale scan and
  the switch pause new charges; the restricted portal role runs checkout,
  webhooks and reconciliation; the routes exist only in a YooKassa market.
- 54-FZ receipt, env, return URL, no provider bodies in logs, kopecks without
  floats, global builds refusing YooKassa settings (LR-67a) — done.
- RU ingress (Caddy handle + `scripts/test_ru_ops.py`), env example, `ru_host.py`
  checks, runbook, account-api README, OpenAPI — done.

## Remaining, host and owner

- **LR-67c (portal)**: the `/supporter` page calls the checkout with a fresh
  `Idempotency-Key` per purchase, sends the quote from the dashboard's
  `yookassa`/`catalog` data, handles `409 reload` by reloading, and on
  `?paid=1` may poll `GET /v1/me/supporter/yookassa/payments` (it re-reads the
  newest payment). The portal BFF allowlist needs both session routes.
- **Owner**: the YooKassa shop of an ИП or ООО with «Чеки от ЮKassa», the VAT
  code, the webhook URL `https://account.omoba.ru/v1/supporter/yookassa/notifications`
  with `payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled`,
  `refund.succeeded`, a test shop, the public offer, and a real payment whose
  fiscal receipt is checked before announcing. Nothing here talked to YooKassa:
  the real API shapes are from the reference integration and YooKassa's docs and
  are unverified against a live or test shop.
- **Host**: fill the shop settings in `/opt/omoba-ru/account-api.env` with
  `NEW_CHARGES=0`, watch one refund scan succeed, run the test-shop flow, then
  switch to `1` (runbook "YooKassa"). The receipt e-mail is stored with each
  attempt; the privacy policy (LR-04) should name it.
- **Monitoring** (LR-17 follow-up, not done here): alert on open
  `supporter_yookassa_issues` and on a stale `last_successful_at`.
