# LR-14: client update path

Goal: implement [LR-14](../plans/launch-readiness.md) with launch default O-12.
Client and server ship together. An incompatible game shows **Update required**
with a download button to the market portal's `/download` for its platform. A newer
compatible release shows a dismissible banner. The source is the market's release
catalog (`GET /v1/releases` of the Account API compiled into the build). Branch
`feat/lr-14` (omoba-bevy).

## Before

- The client never checked for a newer version. A contract mismatch said "Update
  the game or choose another server", but production builds have no server choice.
- Menus stopped retrying after any mismatch, including a game newer than the server.
- Nothing used the release catalog, portal `/download` or `open_external_url` for
  updates. There was no minimum release or update URL anywhere.

## Design decisions

- **Reply, not a signed document.** The compatibility report gets an optional
  `update` object, `UpdateNotice { min_release, url? }`. It is additive:
  `serde(default)`, skipped when absent, older clients ignore unknown fields, so
  `HANDSHAKE_VERSION` stays 1. A test decodes the new bytes with the pre-LR-14 type.
  The server sends its own release as `min_release` (client and server ship
  together). The `url` is `<portal>/download`, built from the `OMOBA_PORTAL_ORIGIN`
  that `release.py` compiles into the market's Linux package, the server included.
  It is sent only while the reply still fits the request (no amplification).
- **The reply stays unauthenticated**, so the client drops a notice whose release
  does not parse or whose link is not plain HTTPS. It opens a notice link only when
  the link lies on its own trusted portal. Otherwise it builds
  `<portal>/download?platform=<platform>` itself (`shared::compatibility::download_page`,
  the one place the link is built). A fragment would be refused by
  `open_external_url`, so the platform goes in the query.
- **Direction of a mismatch** (`shared::compatibility::mismatch_side`): the client
  updates unless it is strictly newer than the server's release and not below the
  server's stated minimum. Unreadable labels, and equal labels with another contract
  (dev builds), ask for an update. A newer game sees "the servers are switching to
  your version", and Home retries every 30 s, because clients now ship first.
- **Catalog** (`passport/src/release_catalog.rs`): read over the build's HTTPS
  Account API at boot and after an update-required mismatch, at most once a minute.
  A malformed, oversized (>128 KiB) or too long (>32) document is refused. Rows with
  an unreadable version or a non-HTTPS link are skipped. The newest row for the
  platform wins, and `universal` (the Android APK) matches any architecture.
  Platform names mirror `release.py` `CATALOG_PLATFORMS`, and a Python test keeps
  them in step. A build without an Account API (global production today) never asks
  and shows no banner. Its mismatch still shows Update required.
- **Market neutrality (LR-68).** No new market comparison. Everything market-specific
  comes from the compiled endpoints (`OMOBA_ACCOUNT_API_URL`, `OMOBA_PORTAL_ORIGIN`
  from `scripts/markets.py`) through `WebAccountApi::from_env`. A runtime region
  only has to supply another portal and API.
- **iPhone** gets no link. The panel says to update through the App Store or
  TestFlight. There is no catalog entry for iOS. The link is always a download page,
  never a payment page.

## Changes

- `shared/src/compatibility.rs`: `UpdateNotice` (`current`, `valid`),
  `download_page`, `valid_update_url`, `ReleaseVersion` (SemVer precedence, build
  metadata ignored), `release_order`, `MismatchSide` and `mismatch_side`,
  `response_with_update`, `ServerReport` and `CompatibilityProbe::accept_report`.
  `response` and `accept` keep their behaviour.
- `server/src/public_transport.rs`: the probe answer carries `UpdateNotice::current()`.
- `shared/src/protocol.rs`: `JoinRejection` English texts no longer mention choosing a
  server or "map release" (they equal `error.json`).
- `passport/src/web_account.rs` `get_bytes`, new `passport/src/release_catalog.rs`.
- Client:
  - `net/transport.rs`: the probe keeps the notice (`NetThreadSignal::Compatibility.update`).
  - `net/session.rs`: `server_update` and `compatibility_verdict()`, which returns
    `Unverified`, `UpdateRequired` or `ServersUpdating`.
  - `net/status_ui.rs`: `LinkStatus::Compatibility(CompatibilityVerdict)` and the
    verdict lines. The per-category text is now a Settings diagnostic
    (`compatibility_reason`, `pause_menu.rs`).
  - `update.rs` (new, `ClientUpdatePlugin` in `NetPlugins`): `ClientUpdate`, with the
    catalog read and the offer (`Required` / `Available`), the link rule, open, and
    **Later**.
  - `frontend/home.rs`: Update required replaces Play with **Download update**
    (`HomeUpdate`) and shows the panel `HomeUpdateRequired`: title, current version,
    and the newest catalog version. **Update available** uses the invite's banner slot
    (`HomeUpdateBanner`, **Download** / **Later**). An invite keeps priority, and on
    phones the banner replaces the recent-match chip like the invite does. The pill
    reads «Требуется обновление» or «Серверы обновляются». The invite banner and the
    update banner share `spawn_choice_banner`.
  - `frontend/mod.rs`: menus keep retrying every 30 s while the servers are updating.
    An older game never retries.
  - `client/i18n/{en,ru,zh-Hans}/update.json` is a new namespace. `net.json` and
    `error.json` are reworded without server choice, and the unused
    `net.compatibility.incompatible_short` is removed. The zh-Hans text stays inside
    the display font subset.
  - `session_config.rs`: one test literal is capitalised (`Lobby.omoba.ru`). On dev,
    the i18n key scan read `lobby.omoba.ru` as a missing `lobby.*` key and failed
    `every_key_shaped_literal_in_client_src_exists_in_english` (since the omoba.ru
    rename).
- `scripts/test_release.py`: the client's catalog platform names mirror `release.py`.
- Docs: `RELEASING.md` gets "Updates and contract changes (LR-14)". It covers what
  bumps `GAMEPLAY_REVISION` and the other revisions, and the order: stage and verify
  the server, ship the clients and the catalog, notify players, switch the servers.
  It also records the O-12 alternative. Also updated: `release-compatibility.md`,
  ADR-013 (amended), `architecture/protocols.md`, `system.md`, `build-and-release.md`,
  `account-api/README.md`, `ops/vps/ru/README.md`, `features.md`, and the LR-14
  acceptance in the plan.

New tests:
- shared: SemVer order, mismatch direction, notice validation, a report with a good,
  bad or forged notice, a stale-nonce report refused, additive wire compatibility.
- passport: newest per platform, bad documents refused, bad rows skipped, empty and
  stale catalogs, the read over loopback HTTP (200, 503, oversized, not JSON).
- server: the probe answer carries `UpdateNotice::current()`.
- client: link rule (own portal only, platform query, iPhone none), offers (required,
  servers updating, unverified, banner until Later), the catalog read at boot and
  after a mismatch, the verdict lines, menu retry while servers update, and the Home
  UI tree in Russian (Требуется обновление, Скачать обновление, the opened link)
  plus the banner with Later.

Visual checks were not done: the Mac's screen is locked and native captures render
black. The layouts reuse the existing Play-button node and the invite banner slot.

## Remaining (needs host / owner)

- **Host:** install the RU `releases.json` (`OMOBA_RELEASE_CATALOG`) on the RU
  Account API before the first contract-changing server switch. Then RU checklist
  P8 proves the prompt end to end against `https://omoba.ru/download`.
- **Host / LR-23:** the portal's `/download` page ignores `?platform=` today. It
  lists every package, so the link works. Highlighting the player's platform is a
  portal change.
- **Owner:** the player notice channel and lead time before a forced update
  (RELEASING.md says "at least the banner period"), and O-12 itself (balance in
  server data) stays open as a later decision.
- `net.status.waiting` (floating in-match panel) still names `GAME_SERVER_ADDR`. It
  is a developer line that does not suggest choosing a server, so it was left as is.
