# LR-22: RU web entry point, Russian README and the RU server bundle

Goal: implement [LR-22](../plans/launch-readiness.md) before the RU host exists, with the
section 7 default "the RU landing is the RU portal's guest home at `omoba.ru`". Branch
`feat/lr-22` from `origin/dev` in both repositories; lane C, so no Rust was built or run.
The portal half is omoba-web `feat/lr-22` (its session note
`docs/progress/2026-10-24-lr-22-web.md`); it builds on the open LR-06 portal PR
(omoba-web #19), which must merge first.

## Changes (game repository)

- `scripts/markets.py`: `Market.player_readme` (`playtest` | `ru`; RU = `ru`) and
  `Market.server_bundle` (a market with its own Account API runs its own servers). Both
  are the one place each decision lives, so LR-68 can switch them to the runtime region.
- `scripts/release.py`:
  - `player_readme` returns the Russian README for a production build of a market whose
    `player_readme` is `ru` (`ru_player_readme`): release status («Открытая бета») and the
    age sign at the top; what the game is, with the class count read from
    `shared/assets/catalog/heroes.json` (17), the Verdant Arena and the modes named by the
    game's own `client/i18n/ru` strings; install (the catalog's Russian instructions, the
    macOS quarantine command, the Linux unpack line); sign-in with VK ID and recovery, named
    by the game's buttons («Профиль» → «Войти через VK ID», «Привязать или восстановить
    аккаунт»; only with the `vk_sign_in` feature); the support and community channels that
    are set plus the portal; system requirements of that package (`MAC_MIN_SYSTEM` also
    feeds the Info.plist, `LINUX_MIN_GLIBC` of the bookworm build image, the APK manifest's
    minimum API and Vulkan, the render backends the game compiles); documents, the release's
    source tag and the age sign. No hosting notes. Dev builds keep the English tester README.
  - `readme_gaps`: `build` prints a note while the owner has not provided the support
    e-mail and a community (LR-21); the dry-run plan lists them.
  - The RU Linux player package no longer carries `omoba-account-api` (`linux_tools`: the
    dev contour only). New target `build server` (also in `build all` for a market with its
    own servers): `build_server_bundle` builds `server` and `omoba-account-api` in one
    invocation with the market's environment (`linux_release_binaries`, the old
    `build_linux` build half, natively or in Docker) and stages `omoba-server`,
    `omoba-account-api`, the legal notices, `ATTRIBUTION.md` and an operator README into
    `dist/v<v>-ru/server/omoba-<v>-ru-server-linux-x64.tar.gz` with its own
    `SHA256SUMS.txt`. `draft` and `publish` look only at the top folder, so the bundle is
    never attached to the release or offered as a download. Dev and global refuse it.
- `ops/vps/ru/ru_host.py`: `ship` accepts only the server bundle (`RU_PACKAGE`, folder
  `omoba-<v>-ru-server/`); the kit refuses `OMOBA_SITE_URL` in `portal.env.example`, which
  now says why it is absent.
- Docs: `ops/vps/ru/README.md` (new [Server bundle](../../ops/vps/ru/README.md#server-bundle),
  step 2), `release-checklist.md` (S2, S3), both unit comments, `docs/markets.md` (packages,
  runbook steps 4, 5, 7), `docs/architecture/build-and-release.md` (crate table, staging,
  artifacts, builders, lobby binaries), `docs/architecture/system.md` (RU lobby),
  `docs/features.md` (LR-22 section), the plan's LR-22 acceptance, `Makefile` help.
