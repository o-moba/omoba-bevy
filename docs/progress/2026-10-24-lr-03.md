# LR-03: off-host backups, secrets escrow and the restore drill for the RU host

Goal: implement [LR-03](../plans/launch-readiness.md) before the RU host exists. The
database and the match and outbox archive go off-host every night and before every
migration, encrypted, to storage in Russia (14 daily and 8 weekly kept). A restore drill
runs every month. The secrets go to an escrow holder. Missing or failed backups raise
an alert. Branch `feat/lr-03` from `origin/dev`; lane C, so no Rust was built.

A first attempt stopped at a usage limit and left the work uncommitted. This session
merged `origin/dev` (the omoba.ru rename), reviewed that work, kept most of it, fixed what
is listed under "Review" and wrote the docs.

## Changes

- `ops/vps/ru/ru_backup.py` (new) runs on the host as root and reads only
  `/opt/omoba-ru/backup.env`. It has no hostnames and no market logic: the RU names stay
  in `scripts/markets.py`.
  - `backup [--reason nightly|pre-migration|manual] [--release R] [--local-only]`:
    - It writes one set, `omoba-ru-<UTC>-<reason>.tar.gpg`, holding:
      - `database.dump` (`pg_dump -Fc` of `omoba_ru`, career and portal)
      - `state.tar.gz` (`/var/lib/omoba-ru/matches` with `archive/` and every allocation
        `outbox/`, and `/var/lib/omoba-ru/lobby-outbox`)
      - `manifest.json` (rows and an order-independent digest per table, read from the
        dump's COPY data, both schema version lists, sha256s)
    - The set is encrypted with GnuPG to the backup public key and signed with the
      backup secret key.
    - It goes to `OMOBA_BACKUP_TARGET`. Supported targets:
      - `s3://bucket/prefix`: S3-compatible storage, SigV4 path-style requests with
        stdlib only, size checked after upload
      - `sftp://user@host[:port]/folder`: OpenSSH `sftp -b` with a pinned host key
      - `file://` for tests and mounts
    - Retention is the newest set of each of the last 14 days that have a set and of
      each of the last 8 ISO weeks. Counting days that have a set means failed nights
      never delete good sets. The host keeps the newest 2 sets.
    - A set that cannot be uploaded stays on the host and goes up on the next run.
    - The run fails if a migration ran during the dump: the schema versions in the dump
      differ from the live ones.
    - Before a migration it also keeps a plain rollback dump (the newest 3 are kept).
      `--local-only` keeps only that dump, for use before launch without storage.
  - `drill [--set NAME] [--from remote|local]`:
    - Downloads the newest off-host set and restores it into `omoba_ru_restore_drill`
      (created with the live database's encoding and locale provider).
    - Compares tables, row counts, every table's row digest (from a re-dump), both
      schema version lists and the state archive with the manifest.
    - Drops the scratch database whether the drill passes or fails.
  - `check [--remote] [--alert]` reports: no backup in 26 h, a failed or interrupted
    run, a failed drill, no successful drill in 35 days, a missing or stale escrow,
    incomplete settings and, with `--remote`, empty or stale off-host storage.
  - `config`, `list`, `fetch --set NAME|latest --out DIR` (the restore path),
    `escrow --recipient-file FILE|- [--file …]` (the Android keystore uses `--file`)
    and `keygen` (ed25519 signing key plus a cv25519 encryption subkey).
  - Alerts always go to the journal (`<3>` priority). When `OMOBA_TELEGRAM_BOT_TOKEN` and
    `OMOBA_TELEGRAM_CHAT_ID` are set they also go to Telegram: one message per problem
    at most every 6 h, and one when every check passes again. No secret is printed,
    logged or passed in argv; tokens are redacted.
- Units, each `Type=oneshot` with `ProtectSystem=strict`, writable only in
  `/var/backups/omoba-ru`, `PrivateTmp` and `NoNewPrivileges`:
  - `omoba-backup-ru.service` / `.timer`: nightly at 00:30 UTC, `Persistent=true`
  - `omoba-restore-drill-ru.service` / `.timer`: the 2nd of the month at 02:30 UTC,
    `Persistent=true`
  - `omoba-backup-check-ru.service` / `.timer`: hourly
- `ops/vps/ru/backup.env.example` (new) contains placeholders only. `ru_host.py kit()`
  refuses unknown keys, real secrets in it, or key paths outside
  `/opt/omoba-ru/backup-keys`.
- `ops/vps/ru/ru_host.py`:
  - `bootstrap` installs the tool, its units and timers, `gnupg` and the folders
    `backup`, `backup-keys` (0700) and `/var/backups/omoba-ru` (root 0700). It writes
    `backup.env` once from the example and never replaces it. The kit is sent
    zlib-compressed in the payload and validated on both sides.
  - `ship` is the pre-migration hook. When a schema exists, it runs
    `ru_backup.py backup --reason pre-migration` instead of a bare `pg_dump`, and it
    refuses to migrate while backups are not configured or the backup fails. Nothing has
    been stopped or migrated at that point. `--local-backup-only` keeps only the rollback
    dump, for use before launch.
  - `status` reports the installed kit, the timers, the `backup.env` mode and
    `ru_backup.py check --remote`.
  - `escrow --recipient-file holder.asc --out FILE` encrypts the secrets on the host to
    the escrow holder's key and saves only the ciphertext on the Mac (0600, never
    overwritten).
- Docs:
  - `ops/vps/ru/README.md`: Backups, escrow and restore drill (what, where, when, kept),
    one-time owner setup, the escrow-holder table, restore on this host and onto a new
    host
  - `RUNBOOK.md`: new section "RU host backups and restore"
  - `docs/architecture/data.md`: RU host subsection; the production-backups open
    question updated (RU has no WAL archiving, so up to a day of data can be lost)
  - `docs/architecture/system.md`: RU host text and a Backups row
  - `docs/markets.md` runbook step 5, `ops/vps/ru/release-checklist.md` S3 and S5,
    `account-api/README.md`, `docs/public-mvp.md`, the RU section of `docs/features.md`,

## Review of the earlier attempt (fixed here)

- **Forged sets could run SQL as the database superuser.** The earlier sets were only
  encrypted to the public key. Anyone with that key or with write access to the
  storage could plant a set, and the monthly drill would `pg_restore` its dump as
  `postgres`. Sets are now signed with the backup secret key, which the host already
  holds for the drill. `fetch` and the drill refuse a set without that signature and
  keep nothing they unpacked from it. The host key files are renamed to the names
  `keygen` gives them (`backup-public.asc`, `backup-secret.asc`), and `config` now
  always checks the secret key, so the `--for backup` option was removed.
- **SFTP re-upload.** Re-uploading a set whose remote copy had the wrong size would fail,
  because SFTP v3 `rename` never replaces a file. The wrong copy is now removed first.
- `key_info` no longer starts a gpg-agent, and only the agent is stopped after secret-key
  work. The backup tests went from 96 s to about 30 s.
- `MacEscrowTest` sat after `unittest.main()` and did not run when the file was run
  directly. It is moved above it.
- The PostgreSQL round-trip test applies every migration file it finds, so the career
  004/005 and portal 008/009 migrations reserved for M0 are covered once they land.
