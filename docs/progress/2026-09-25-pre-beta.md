## O4: standalone pre-join endpoints (behaviour change)

- Found: `GameWorld::ensure_connected` (`server/src/session.rs`) inserts a
  `ConnectedPlayer` for any source address with no limit, and it is called
  from the `Hello`, `Ping`, `Transform`, `Cast`, `Join` and other handlers.
  `broadcast_snapshots` sent every non-bot endpoint in a standalone server
  (`MatchService::Standalone`) the full vision-filtered snapshot (structures,
  minions, neutrals, projectiles, events, scoreboard) every
  `SNAPSHOT_INTERVAL` (50 ms) until `PLAYER_TIMEOUT` (5 s): about 100
  snapshots per datagram, with `0.0.0.0:4000` as the default bind. Public
  roles filter recipients through `public_transport.validated` and
  `gameplay_principal`, so they were not affected.
- Fix: `server/src/runtime/prejoin.rs`. An endpoint is verified when it has
  joined or holds an authenticated career session.
  `admit_standalone_datagram` runs in `handle_packet` after the career and
  social early returns: in a standalone server a datagram from a new address
  is dropped (rate-limited log line) while `MAX_PREJOIN_ENDPOINTS` (64)
  unverified endpoints exist, and an accepted datagram from an unverified
  endpoint marks one status reply as due. `broadcast_snapshots` sends the
  world only to verified endpoints in a standalone server; then it sends each
  unverified endpoint with a due reply one status snapshot, at most once per
  `PREJOIN_STATUS_INTERVAL` (250 ms). The status snapshot is the existing
  `ServerPacket::Snapshot` with meta, `match_mode`, `geometry_id`,
  `map_profile`, `your_id`, `join_error` and `game_state`, and empty
  players and world lists (no new wire variant). It is framed after `Hello`,
  like every snapshot. The sending code moved into a free `send_snapshot`
  that both paths use. Public roles are untouched: the admission
  helper returns early and the recipient filter keeps their branch.
- Client and harness compatibility: the client heartbeats `Hello` every 2 s
  and waits for any snapshot before it counts as connected; it reads
  `ProtocolMismatch`, `MapGeometryMismatch` and the other rejections from
  the status reply. The harness bots `Hello`/`Ping` and then `Join`; the
  harness suite passes unchanged, including the release lifecycle test that
  waits for `session_active` and `match_full` on unjoined peers.
- Tests (`server/src/runtime/prejoin/tests.rs`, `ServerRuntime::for_test` +
  `MemoryTransport` + `ManualClock`):
  `burst_from_unjoined_addresses_keeps_at_most_the_limit_and_one_small_reply_each`
  (104 addresses × 3 datagrams: 64 kept, one status reply each, the rest
  dropped with no reply),
  `a_silent_unjoined_endpoint_gets_one_reply_not_a_snapshot_stream` (one
  datagram, then 5 s of ticks: exactly one reply; the old code sent one per
  interval), `a_chatty_unjoined_endpoint_gets_at_most_one_reply_per_interval`,
  `a_rejected_hello_is_reported_in_the_status_reply` (framed reply carries
  `protocol_mismatch`) and
  `a_joined_player_still_gets_full_snapshots_beside_unjoined_strangers`
  (one full snapshot per interval with structures and the player, while the
  64 admitted strangers get only status replies).
- Limitation: a spoofed flood can still fill the 64 slots for 5 s after it
  stops and delay new joins on a LAN host during that time; joined players
  and their snapshots are not affected.

## O6: skipped Python tests in CI

- Found: CI ran only `scripts/`; the 42 `mobile/ios` tests never ran. In
  `scripts/test_candidate_assets.py`, `setUpClass` raised `SkipTest` for
  the whole class (28 tests) when `OMOBA_DENIED_ASSET_ROOT` was unset, so
  its `git show f2a3359:…` fallback could not run even in a full clone.
  Only `test_every_denied_binary_and_preview_fails_when_renamed` uses the
  denied bytes.
- Fix: the denied bytes are loaded lazily by that one test
  (`denied_fixture()`): `OMOBA_DENIED_ASSET_ROOT` first, then
  `git show f2a3359:…` (works in a full clone), otherwise the test skips;
  bytes that are present but do not match the reviewed hashes are still an
  error. The other 27 gate tests run everywhere. The CI `scripts` job and
  `make test-scripts` also run `mobile/ios`.
- Not done: providing the denied bytes in CI. No denied files are
  committed, and this change adds no CI step that obtains them (fetching
  them was not permitted in this session). Whether CI should provide them
  (for example through `OMOBA_DENIED_ASSET_ROOT`) is left to the
  maintainer; until then that one test skips with a message saying so.
- Result: Python script tests 96 → 124 (1 skipped), `mobile/ios` 42.

## O24: mobile compile checks

- Found: 38 `target_os` lines in 9 client files and the StoreKit FFI were
  compiled by no CI job.
- Local Android attempt (`rustup target add aarch64-linux-android`, then
  `cargo check -p client --target aarch64-linux-android --locked`): fails in
  build scripts, not in our code. `cargo check` does not link, but
  `blake3` (NEON C), `ring` (C) and `oboe-sys` (C++ against the NDK's
  AAudio headers) compile native code for the target. With the host
  clang and aarch64 glibc headers standing in for the NDK, the first
  failure moved to `oboe-sys`, which needs `aarch64-linux-android-clang++`
  and the NDK headers. The NDK download is blocked by the session's
  network policy (403), so the Rust client code could not be checked for
  Android here; the CI job is the first real run.
- Fix: CI job `android` (push and PR) installs the target, points
  `CC/CXX/AR_aarch64_linux_android` (and the linker, for later builds) at
  the NDK preinstalled on `ubuntu-latest` (`$ANDROID_NDK_LATEST_HOME`,
  falling back to `$ANDROID_NDK_HOME`, API 26 like `mobile/android/build.py`)
  and runs the check. `.github/workflows/ios-check.yml` runs
  `cargo check -p client --target aarch64-apple-ios --locked` on
  `macos-latest` weekly (Monday 04:41 UTC) and on `workflow_dispatch`; it is
  not a PR gate. The report's "first run once by hand on a Mac" is now the
  first manual dispatch of that workflow.
- Note: if the `android` job becomes a required check, branch protection
  needs it added next to the four existing checks.

## O10: enum evolution policy

- Found: of the serde enums in `shared`, most decode strictly, and the
  client drops a whole datagram when any field fails to decode; nothing
  forced a decision when a variant was added.
- Fix: `shared/src/protocol/wire_enums.rs` (declared from
  `shared/src/protocol.rs`; `wire.rs` is not edited). `wire_enums!` lists
  the 43 enums reachable from `ClientPacket`, `ServerPacket`,
  `PublicClientDatagram` and `PublicServerDatagram` with their variants and
  strict or tolerant decoding, and generates an exhaustive `match` with no
  `_` arm for each, so a new variant fails to compile there (checked by
  removing `Aggro` from the list: E0004). `POLICY_PROTOCOL_VERSION` pins the
  list to `PROTOCOL_VERSION`. A source scan finds every `pub enum` in
  `shared/src` that derives or implements `Deserialize` and fails when one
  is neither listed nor in `NOT_UDP_WIRE` (9 enums: account-api HTTP
  contracts, catalog, map and sprite-roster data), checked by removing
  `Placement`. Tolerant enums (6) must decode an unknown value; strict
  ones reject it. Rule added to `ARCHITECTURE.md` "Protocol rules".
- `CharacterChoice` is the SDK's `EkzaCharacter`, defined outside `shared`,
  and is not listed. If step 13 turns it into an enum in `shared`, the scan
  will ask for it to be classified after the merge.
- Tests: shared 94 → 99.
