# LR-17 (ops part): alerts, external probe and journal limits for the RU host

Goal: the ops half of [LR-17](../plans/launch-readiness.md) before the RU host exists. The
owner learns of an outage within minutes without logging in, and the journal is bounded.
The lobby's own signals (database status file, `QUEUE_METRIC`, archive retention,
`worker.log` cap) are the server part (lane A) and are not in this branch. Branch
`feat/lr-17-ops` from `origin/dev`; lane C, so no Rust was built.

## Changes

- **Host alerts**: `ops/vps/ru/ru_monitor.py` (new) runs on the RU host as root and reads
  only `/opt/omoba-ru/alerts.env`. It has no hostnames and no market logic.
  - `unit-failed UNIT` is the `OnFailure=` handler. `omoba-alert-ru@.service` (new) runs
    it for `omoba-alert-ru@<unit>.service`. The message names the unit, the result and
    exit status (`MONITOR_*`, systemd 251+) and what systemd does next. It is sent at once,
    then at most hourly for a service and daily for a timer job, whose own tool sends the
    details.
  - `check [--json] [--alert]` runs every 5 minutes (`omoba-monitor-ru.service` and
    `.timer`, new). It reports:
    - an enabled RU service, PostgreSQL or Caddy that is not running
    - a failed backup, drill or backup-check run
    - a disabled or stopped backup timer, which makes no backup and silences the
      missing-backup alert
    - free disk below 15% on every filesystem the host writes to (one problem per
      filesystem)
    - a live match worker (phase ready … recovering) whose `status.json` heartbeat is
      older than 5 minutes, checked only while the lobby has run that long
  - Reminders are hourly (daily for timer jobs). A "resolved" message is sent once a
    problem has not been seen for 15 minutes; a unit must also be settled (active, or
    inactive without failing). State lives in `/var/lib/omoba-ru-monitor` (systemd
    `StateDirectory`, under a lock).
  - `test-alert` sends one message to prove the bot works.
  - Messages carry unit names, paths, numbers and allocation ids only, never a log line,
    an address or a secret. The token is redacted everywhere.
- **`OnFailure=omoba-alert-ru@%n.service`** in every RU unit: lobby, Account API, portal,
  backup, restore drill, backup check and the host check. The template has none (it
  would loop). `ru_host.py` refuses a kit unit without it.
- **One Telegram bot**: `alerts.env.example` (new) holds the bot and the thresholds.
  `ru_backup.py` now falls back to that bot when `backup.env` names none
  (`OMOBA_ALERTS_ENV`), so the backup alerts (LR-03) share it. `backup.env.example`
  says so.
- **Journal limits**: `journald-omoba-ru.conf` (new) is installed as
  `/etc/systemd/journald.conf.d/50-omoba-ru.conf`: `Storage=persistent`,
  `SystemMaxUse=1G`, `SystemMaxFileSize=64M`, `MaxFileSec=1day`, `MaxRetentionSec=30day`.
  LR-04 must name the 30 days, because some lines carry IP addresses.
- **`ru_host.py`**:
  - `kit()` sends a second compressed kit (`monitor_kit_z`: the tool, three units,
    `alerts.env.example`, the journald drop-in). Both sides check it: unit rules, the
    template without `OnFailure=`, `Storage`/`SystemMaxUse`/`MaxRetentionSec`, a
    placeholder-only example, and `ru_monitor.py`'s units and folders matching
    `ru_host.py`'s.
  - `bootstrap` installs the kit before the units that name its template. It writes
    `alerts.env` once (never replaced), installs the drop-in, restarts
    `systemd-journald`, and enables and starts the monitor timer.
  - `status` reports the kit, the timer, the `alerts.env` mode, the drop-in, and the
    disk and worker findings of `ru_monitor.py check`. Its unit findings are status's
    own checks.
  - The payload is 85.6 kB, below the test bound of 100 kB.
- **External probe**: `scripts/market_probe.py` (new) is one stdlib file for Python 3.9+.
  - `config --market ru [--out FILE]` writes the probe host's settings from
    `scripts/markets.py` (0600, never replaced). It refuses markets without their own
    servers.
  - `check (--market | --env-file)` runs one round without state.
  - `run` is the timer's round. Each check alerts after 2 failed rounds in a row
    (`OMOBA_PROBE_FAILURES`), reminds hourly and says once when the check answers again.
  - The checks are the lobby's UDP compatibility probe (the JSON exchange from
    `shared/src/compatibility.rs`: 32-hex nonce, a valid placeholder contract, 512
    padding, resent every 0.5 s for 4 s, connected socket, only a correlated valid
    report counts), `/health/ready` (200) and the portal (200–399).
  - `ops/probe/omoba-probe@.service` and `.timer` (new) run it every minute as a
    `DynamicUser`, with the root-only `/etc/omoba-probe/<market>.env` as their
    `EnvironmentFile`. `ops/probe/README.md` (new) covers installation on a machine
    outside the RU host and an end-to-end alert test.
- **`release.py preflight`** adds `lobby_udp`, the same UDP check on the address DNS gave.
  `--contract dist/v<v>-ru/compatibility.json` sends that release's contract and requires
  a compatible server (`read_contract` validates the file).
- **Docs**:
  - `ops/vps/ru/README.md`: status, "What runs where", bootstrap, Check and a new

  - `ops/vps/ru/release-checklist.md`: S6 now includes UDP; new row S12 (alerts, probe,

## Review fix, round 1

- Problem: a server answering non-HTTP bytes made `http.client` raise `BadStatusLine`
  (or `LineTooLong`, other `HTTPException`s), which urllib does not wrap. It escaped
  `run_checks`, so `run_round` never saved its state or alerted, and every round of
  `omoba-probe@ru.service` ended in a traceback with no alert.
- `market_probe.http_check` catches `http.client.HTTPException` (error = class name);
  `run_checks` turns any other exception of one check into a failed check, keeping the
  others. `run_round` saves the state before Telegram is tried, and the Telegram send
  times out after 10 s (was 20 s), so a round's socket timeouts (4 + 2 × 8 + 10 s) leave
  20 s of `TimeoutStartSec=50s` for name lookups.
- Same gap closed in `market_probe.telegram`, `ru_monitor.py`'s Telegram send and
  `release.py preflight`'s HTTP checks.
- `ops/probe/README.md`: a non-HTTP reply is a failed check.
- Tests: a loopback TCP server answering `garbage\r\n\r\n` (and an over-long status
  line) fails the check; a round against it keeps the lobby result, saves its state before
  the send and alerts on the second round; a raising check fails alone; garbled Telegram
  replies in both senders; preflight with a non-HTTP reply; the unit's time budget.
- Checks: `python3.13 -m unittest discover -s scripts -p 'test_*.py'`: 591 tests, only
  the known `test_sync_ui` failure (sibling omoba-ui checkout), 8 skipped.
  `/usr/bin/python3` (3.9.6) `test_ru_backup test_ru_host test_ru_ops test_ru_monitor
  test_market_probe`: 141 tests OK, 11 skipped. No cargo (lane C).
