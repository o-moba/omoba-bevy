# LR-23: RU-hosted downloads, the «Открытая бета» label and download counts

Goal: implement [LR-23](../plans/launch-readiness.md) before the RU host exists. RU
packages are downloaded from the RU host (`omoba.ru/downloads/`, Caddy `file_server` on
the RU portal site), IPFS becomes the mirror, the catalog shows the status «Открытая
бета» (section 7) and downloads are counted per platform. Branch `feat/lr-23` from
`origin/dev`; lane C, so no Rust was built or run.

## Changes

- `scripts/markets.py`: the RU profile gets `downloads_path="/downloads"` and
  `release_label="Открытая бета"` (global keeps `playtest`). `Market.downloads` is
  `<portal><downloads_path>`, so the download host is no fourth DNS name and moves with
  a portal rename. `Market.region` is the one accessor for the catalog's region (LR-68
  swaps it for the runtime region).
- `scripts/release.py`:
  - `publish` for a market with a download host (prod contour): needs
    `--rsync-target [user@]host:/folder` (or `OMOBA_DOWNLOADS_RSYNC_TARGET`). The target
    is refused on the production VPS, `$DEV_IP`, dev names and other markets' or global
    names, also through the alias's `ssh -G` HostName. It stages the packages (no `.ipa`)
    as `v<version>/` (folder 0755, files 0644), runs `rsync -r -t -p --ignore-existing -e
    "ssh -o BatchMode=yes …"` (flags macOS's openrsync also accepts; checked locally),
    downloads each package from `<portal>/downloads/v<version>/<file>`, compares SHA-256
    and size and records `downloads.json`. Already verified packages are skipped; a
    rebuilt package under a published name fails the read-back instead of replacing the
    file. Then the IPFS pin runs as before. `--dry-run` prints the rsync command and the
    URLs and contacts nothing.
  - `catalog`: a market with a download host lists `downloads.json` (the URL must be its
    host's exact `<downloads>/v<version>/<file>`), with the IPFS copy of the same SHA-256 as
    `mirror_url`. Every entry gets `test_status` = the market's `release_label`, `region`
    and `channel` `direct` (section 7 "Rules for M0 items": LR-23).
  - `verify-downloads [--market ru] [--catalog file|https]` (new): reads what the portal
    serves (`<portal>/api/releases`), downloads every package and its mirror and checks
    host, region, channel, status, SHA-256 and size; ready only when every RU platform is
    listed and correct.
- `ops/vps/ru/Caddyfile.ru`: the `omoba.ru` site serves `/downloads/*` from
  `/opt/omoba-ru/downloads` (no listing, dot files hidden, `nosniff`, APK content type,
  one-day cache) and proxies the rest to the portal. Only `/downloads/` requests are
  logged (`skip_log` for the rest) to `/var/log/caddy/omoba-ru-downloads.log`: JSON,
  request headers deleted, address masked to /24 or /48, rolled at 50 MiB, kept 90 days.
  Directives are Caddy 2.6-compatible (Ubuntu 24.04 ships 2.6.2).
- `ops/vps/ru/ru_downloads.py` (new, stdlib only): counts the log and its rolled gzip
  copies: `downloads` (GET 200/206 of a package, once per masked address, file and UTC
  day), `completed` (whole file in one 200) and `requests`, per platform, per version and
  per day. It never prints an address. The package pattern is release.py's
  `artifact_name` for the market (tested against it).
- `ops/vps/ru/ru_host.py`:
  - `bootstrap` creates `/opt/omoba-ru/downloads` (root 0755) and `/var/log/caddy`
    (caddy 0750) and the download log owned by caddy before `caddy validate` (which runs
    as root) could create it root-owned.
  - `status` reports a missing or non-caddy log and lists the published versions
    (`facts.downloads`).
  - `kit()` refuses a portal site without the download path, the folder, the log, the
    header deletion, the address masking or the `skip_log`.
  - `downloads [--since] [--until]` pipes `ru_downloads.py` to the RU host behind the
    usual target guards and prints the totals.
  - The tool still writes no RU name; the path comes from `scripts/markets.py`.
- `Makefile`: `release-ru-publish` passes `--rsync-target "$(RU_DOWNLOADS_TARGET)"`
  (default `${RU_HOST:-vds-ru}:/opt/omoba-ru/downloads`). The new target
  `release-ru-verify-downloads` runs `verify-downloads`.
- `account-api/docs/openapi.json`: the Release schema gets the optional `region`,
  `channel` and `mirror_url`. The Account API already passes unknown fields through
  (`account-api/src/read.rs` checks only the required ones); the game's catalog reader
  (LR-14) ignores them.
- Docs: `ops/vps/ru/README.md` (new "Downloads" section: layout, publish, catalog,
  verify, counting, privacy, the test download from a Russian network; topology and
  "What runs where" rows), `ops/vps/ru/release-checklist.md` (S10 now verifies the host
  and status; new S11 test download from a Russian network; S10–S11 block the
  announcement), `docs/markets.md`, `docs/RELEASING.md`,
  `docs/architecture/build-and-release.md`, `docs/architecture/system.md`,
  `account-api/README.md#downloads`, `docs/features.md`, the plan's LR-23 acceptance.

## Remaining

- **Needs host:**
  - `ru_host.py bootstrap --apply` installs the new Caddyfile (`caddy validate` on the
    real Caddy is the first syntax check of the new site; it keeps the old file if
    refused).
  - Then `make release-ru-publish`, install `releases.json`, and
    `make release-ru-verify-downloads` must say `"ready": true`. Acceptance 1 and 2
    (the portal shows «Открытая бета»).
  - `ru_host.py downloads` after real downloads (acceptance 3).
- **Needs owner:**
  - A test download from a Russian network, recorded with release checklist S11
    (acceptance 4).
  - Confirm or change the label «Открытая бета» (`release_label` in `scripts/markets.py`).
  - The privacy policy (LR-04) must name the download log (shortened address, 90 days).
- **Portal (omoba-web), not in this lane:** show `mirror_url` as a mirror link and
  highlight `?platform=` on `/download` (LR-14 note). The status already shows.
- **Rust follow-up (a cargo lane):** `account-api/src/read.rs` could validate the
  optional `mirror_url` like `url` (HTTPS, no credentials). Today only release.py writes
  it, and the catalog file is root-owned.
- Visual checks: none needed (no UI change in this repository).
