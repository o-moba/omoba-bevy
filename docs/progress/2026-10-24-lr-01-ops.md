# LR-01 (ops): the RU host kit, ready before the host exists

Goal: implement the ops part of [LR-01](../plans/launch-readiness.md) so the RU stack
can be provisioned on a fresh VPS and restarts on its own, before the host is bought.
The code check (public lobby with an unset or loopback public host) is lane A's.
Branch `feat/lr-01-ops`; no Rust was built (lane C).

## Changes

- `ops/vps/ru/omoba-portal-ru.service` (new): the RU portal as its own unit, user
  `omoba-portal-ru`, `Restart=always` without a start limit, `MemoryHigh=448M`,
  `MemoryMax=512M`, `CPUQuota=100%`, `TasksMax=64`, sandboxing (strict, no
  capabilities, private devices), `HOSTNAME=127.0.0.1`, `NEXT_TELEMETRY_DISABLED=1`.
  It runs the bundle's `server.js` directly on `/opt/omoba-ru/node/current/bin/node`,
  so a server crash is a unit crash (no `scripts/start.mjs` wrapper). The only writable
  folder is `CacheDirectory=omoba-portal-ru`, which the release's `.next/cache` links to.
- `omoba-lobby-ru.service`, `omoba-account-api-ru.service`: `After=`/`Wants=postgresql.service`,
  `Restart=always`, `StartLimitIntervalSec=0` (the lobby's `StartLimitBurst=6` in 120 s
  is gone: a slow database at boot no longer leaves it failed for good).
- `ops/vps/ru/lobby.env.example` (new): the lobby's env file contract
  (`OMOBA_DATABASE_URL` for `omoba_game`, `OMOBA_MATCH_PUBLIC_HOST`).
- `ops/vps/ru/ru_host.py` (new), plan/check/apply like `ops/vps/dev/lobby_dev.py`:
  - `bootstrap`: Ubuntu 24.04+ x86-64 only; Ubuntu packages only (`postgresql caddy ufw
    openssh-server`); PostgreSQL 16+ with `und-x-icu`, loopback only, port 5432,
    verified before any secret is written; Node.js ≥ 20.9 from an uploaded official
    tarball (sha256 from SHASUMS256.txt) or Ubuntu's `nodejs` when new enough; users
    `omoba-ru` and `omoba-portal-ru`; folders and modes; env files from the examples
    with database passwords and both secrets generated on the host (root 0600, never
    replaced, only placeholders filled on reruns); roles and database `omoba_ru`
    (UTF8, C.UTF-8); `Caddyfile.ru` after `caddy validate`; key-only SSH drop-in
    (`sshd -t`, `sshd -T`, refused without an authorized key); ufw denying everything
    but SSH, TCP 443, UDP 4000 and the arena range read from the lobby unit (its own
    stale rules are removed); the units; `postgresql` and `caddy` enabled, an OMOBA unit
    once its release exists.
  - `ship --package`: RU Linux package only; immutable staged releases; `pg_dump -Fc`
    before a migration; `omoba-account-api migrate` under a temporary expiring owner
    login; `grants.sql`; switch, restart, verify (UDP 4000, the lobby's exe,
    `/health/ready`); rollback on failure; refuses while a match runs.
  - `portal-bundle` (local) and `ship-portal`: pack and install the omoba-web
    standalone build; both refuse a build that is not `OMOBA_BUILT_MARKET` ru (Ekza
    off) / production, `.env*` files, `.next/cache`, paths outside the bundle folder.
  - `status` (read-only, everything), `reboot-check --apply`, `rollback`.
  - Guards: production and dev aliases, addresses, units, users and folders refused on
    the Mac and on the host; `ssh -G` HostName must be `$RU_IP` and the user root;
    bootstrap asks `whois` for country RU (`--country-confirmed` overrides); later
    runs need `/opt/omoba-ru/host.json` naming market ru and `$RU_IP`.
- `ops/vps/ru/release-checklist.md` (new): the RU release checklist (server gate S1–S10;
  per platform P1–P8: clean install in Russian, VK sign-in, bot match, Casual and
  Ranked, reconnect, update over the previous version, incompatible server; result
  template for `docs/progress/`). `docs/release-gate-checklist.md` is marked historical.
- Docs: `ops/vps/ru/README.md` (status, what runs where, install/update with the tool,
  portal bundle, check, rollback), env examples, `docs/markets.md` runbook steps 1, 5, 6,
  `docs/features.md` (markets section), architecture `system.md` (RU host table, open
  questions), `build-and-release.md`, `data.md`, `methodology.md`.
