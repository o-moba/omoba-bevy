# 2026-10-25 — LR-67a: Hero tier engine and data

## Goal

LR-67 (RU donations through YooKassa with tiered hero auras), part a: everything
except the YooKassa provider flow (LR-67b: checkout, webhook, reconciliation)
and the portal (LR-67c). Contract: `docs/plans/launch-readiness.md` LR-67 (as
amended), section 7 and its "Rules for M0 items so they survive LR-68", ADR-024
and ADR-025.

## What changed

- **shared**
  - `supporter.rs`: `SupporterTier` (Rose 100, Jade 250, Azure 500, Crimson 1000,
    Prism I 2500, Prism II 5000, Prism III 10000) with `for_points`; seven tier
    `AuraStyle` variants (`rose` … `prism_iii`); the entitlement rule
    `AuraStyle::unlocked` (base styles need any active grant, tier styles their
    points), the step-down `AuraStyle::effective`, the default
    `AuraStyle::highest_unlocked`; `SupporterGrantSummary.tier_points`,
    `SupporterStatus.tier_points` and `tier_until` (sweep over grant ends),
    `SupporterStatus::from_grants` (the one builder both readers use),
    `authorized_aura` (the server's check), `STATUS_GRANT_LIMIT` = 64. Old status
    JSON still decodes.
  - Protocol 12: `PROTOCOL_VERSION`, `POLICY_PROTOCOL_VERSION`, `AuraStyle` strict
    list, golden test `protocol_12_carries_tier_auras_and_tier_status`.
  - `market.rs`: `PaymentProvider` (apple, solana, yookassa),
    `Market::payment_providers` (global `[apple, solana]`, RU `[yookassa]`, CN
    none), the accessor `payment_providers()` (empty while `supporter` is off),
    `sells`, `sells_tiers`; RU preset `supporter` on. Pinned describe line:
    `ru (ekza off, supporter on, vk_sign_in on)`.
- **scripts/markets.py**: RU `supporter` on, `payment_providers` per market,
  `payment_providers(key, overrides)`; `test_release.py` checks the provider lists
  against `market.rs`.
- **Account API**
  - Migration `009_yookassa_supporter.sql` (portal schema 9; 8 stays reserved
    for LR-20): provider `yookassa` in both CHECKs, `amount_minor` (YooKassa only),
    `tier_points` (default 0, no backfill), the tier aura ids,
    `portal.supporter_points(profile, at)`, `portal.supporter_months(profile)`,
    `supporter_yookassa_attempts` (request key, Idempotence-Key, payment id,
    amount, RUB, frozen receipt, offer version, status, lease, first provider
    attempt, poll rotation, timestamps), `supporter_yookassa_refunds`,
    `supporter_yookassa_refund_scan` (durable cursor and last success),
    `supporter_yookassa_issues`. `PORTAL_SCHEMA` = `[1..7, 9]`;
    `ops/grants.sql` grants the new tables (no DELETE) and EXECUTE on the functions.
  - `supporter.rs`: `apply_event_tx` stores `amount_minor` and `tier_points` from
    the provider rule, refuses an amount change, and writes the default aura
    (highest unlocked; a recognition placeholder is upgraded on the first grant, a
    hidden aura is kept); `status` uses one read-only snapshot, the SQL tier sum
    and the shared builder; the dashboard adds `providers` and a catalog with
    `tier_points`/`unlocked`; equip refuses a tier style without points
    (`tier_required`). `BillingConfig::check_market` refuses another market's
    provider settings; `provider_route_allowed` 404s another provider's routes.
  - `supporter/yookassa.rs`: shop settings (`OMOBA_YOOKASSA_SHOP_ID`, `_SECRET_KEY`,
    `_VAT_CODE`, `_NEW_CHARGES`, all-or-none), amounts in integer kopecks, the
    points rule, and `settle_payment_tx` / `settle_refund_tx` for re-read provider
    objects: success grants 30 days once, a late cancel never downgrades a success,
    a refund settles its payment first and recomputes or revokes, unknown payments
    write nothing, a lost create binds by attempt id.
  - `recognition.rs`: `months_supported` from `portal.supporter_months` (YooKassa
    donations count distinct UTC calendar months).
- **Career store**: `supporter_status` and `equip_supporter_aura` use the same
  rule, the SQL tier sum and the 64-row bound; no hard-coded `solar`.
- **Server**: `authorized_supporter_aura` is `SupporterStatus::authorized_aura`
  (re-checked every refresh and snapshot); test hook `test_refresh_now`.
- **Client**
  - `supporter.rs`: palettes for Rose, Jade, Azure, Crimson; Prism I–III cycle
    hue on the style's shared materials (three hue offsets, only worn styles
    repainted), speed/glow/sparks growing per tier; Prism III crown replaces one
    spark (budget 23, 2D 35); `payment_surface()` (Website on non-iOS where
    YooKassa is sold, StoreKit for global iOS, else none); panel tier line
    (tier until date, then the next tier, or how donations add up), tier styles
    listed where tiers are sold, locked labels, Equip gated by the rule,
    «Поддержать на сайте» opening `<portal>/supporter`.
  - `plugins.rs`: the StoreKit plugin needs Apple among the providers (RU: panel,
    no StoreKit).
  - i18n: aura names in `aura.json`, panel strings in a new `tier.json` namespace
    (en, ru, zh-Hans, inside the display font subset).
- **passport**: `supporter_account::website_url`.
- **Docs**: `docs/supporter.md` (Hero tiers), `docs/markets.md`,
  `account-api/README.md`, OpenAPI (dashboard, status, 403 `tier_required`, tier
  ids), `docs/release-compatibility.md` (protocol 12, LR-14 order),
  `docs/architecture/{data,decisions,identity-and-accounts,protocols,system,build-and-release}.md`,
  `docs/features.md` (Markets line and Hero Supporter section), `ops/vps/ru/README.md`.

## Acceptance (LR-67, the parts in LR-67a)

- Unit tests: thresholds; window sum with expiry and partial refunds; 1 ₽ = 1
  point and recompute after partial refunds; base vs tier styles; custom amount
  bounds (100–100 000 ₽); provider lists (RU yookassa only, global unchanged);
  the pinned describe line; protocol 12 golden tests — done.
- Account API Postgres tests with synthetic YooKassa objects: duplicate success
  grants once, cancel after success ignored, refund before payment, partial and
  full refunds recompute the tier, unknown payment writes nothing, the restricted
  portal role settles and cannot delete billing rows, the game role can execute
  `supporter_points` — done. Checkout key persistence and the 23-hour replay are
  LR-67b (the tables and `REPLAY_WINDOW_SECONDS` are here).
- Server: a 1000-point grant equips Crimson over signed UDP; Prism I is refused;
  the second client sees Crimson; after expiry the aura disappears within one
  access refresh — done (Postgres-backed live UDP test).
- RU client: `SupporterPlugin` registered, StoreKit not; the panel reads
  `payment_surface()` and opens the portal page; other players' tier auras
  render within the budget — done as UI-tree tests; visual capture not done.

## Remaining, host and owner

- **LR-67b**: `POST /v1/me/supporter/yookassa/checkout`, `GET .../payments`, the
  public notification route (and its Caddy native-list entry), the reconciliation
  loop with refund scan, receipts with `vat_code` from env, the loopback stand-in
  origin. It only adds code on top of these tables and settlement functions.
- **LR-67c** (portal): `market-profile.mjs` still has RU `supporter` off and no
  provider list; its parity tests are hand-written and do not read this repo, so
  nothing fails across repos until it changes. The portal's describe line for RU
  becomes `ru (ekza off, supporter on, vk_sign_in on)`.
- **Release**: protocol 12 means client and server ship together (LR-14 order);
  apply portal migration 9 and `grants.sql` first.
- **Owner**: the YooKassa shop for an ИП or ООО, «Чеки от ЮKassa», the VAT code,
  the webhook, the public offer and a real fiscal-receipt test (LR-67 "Owner").
  Tier names are working names. `months_supported` counts UTC calendar months,
  so a donation made 00:00–03:00 Moscow time on the 1st counts for the previous
  month; switch `portal.supporter_months` to Moscow time if the owner prefers.
- **Host**: nothing in this step touches a host; the RU env example gets the shop
  settings with LR-67b.
