# LR-02: the RU portal reaches the Account API with the real client IP

Goal: implement [LR-02](../plans/launch-readiness.md) before the RU host exists.
Behind `Caddyfile.ru` every RU portal call to the Account API was refused (403),
and once that was fixed the per-IP limits would have keyed on the portal host.
Branch `feat/lr-02` in omoba-bevy and omoba-web.

## Decision

The preferred topology from the spec ([ops/vps/ru/README.md › Topology](../../ops/vps/ru/README.md#topology)):
the portal calls `http://127.0.0.1:40550` directly, `OMOBA_TRUST_LOOPBACK_PROXY=1`
is set on the portal and the Account API, and Caddy on `app.ru.omoba.io` overwrites
`X-Real-IP`. RU has no portal ingress key at all; `account.ru.omoba.io` serves only
the game's native routes and health.

## Changes

- `ops/vps/ru/Caddyfile.ru`: the `@portal` key route is gone; account.ru passes
  `@native` and `@health` and answers 403 to everything else. app.ru keeps
  `header_up X-Real-IP {remote_host}`.
- `ops/vps/ru/portal.env.example`: `OMOBA_ACCOUNT_API_URL=http://127.0.0.1:40550`,
  `OMOBA_TRUST_LOOPBACK_PROXY=1`, no ingress key. `account-api.env.example`
  explains the two loopback clients and why the flag is required.
- `ops/vps/ru/README.md`: a Topology section (who calls what, which address the
  API sees), install steps 5–6 and the Check section updated; the LR-02 blocker
  note removed.
- `scripts/release.py preflight`: for a market with an Account API and a portal it
  also checks `GET <portal>/api/me` = 401, `GET <portal>/api/releases` = 200 (a 403
  on either fails with an LR-02 hint) and `GET <account_api>/v1/me` = 403 (portal
  routes stay off the public name).
- `scripts/test_ru_ops.py` (new): the env examples and `Caddyfile.ru` describe one
  topology (loopback URL = bind, both trust flags, no key, the RU native list,
  X-Real-IP overwritten on both sites).
- Docs: `docs/markets.md` (runbook steps 5–6), `docs/features.md` (markets
  section), `account-api/README.md`, and the architecture pages that described
  the blocker (`system.md`, `protocols.md`, `identity-and-accounts.md`,
  `data.md`, `decisions.md`, `README.md`).
- omoba-web:
  - `src/lib/security.mjs`: `portalConfig` refuses an enabled Account API that is
    not on loopback without a 64-hex `OMOBA_ACCOUNT_INGRESS_KEY` (any contour or
    market), a malformed key even when unused, a trust switch other than `1`, and
    a public-origin portal on the loopback API without `OMOBA_TRUST_LOOPBACK_PROXY=1`
    (`OMOBA_ALLOW_INSECURE_LOCAL=1` test doubles excepted). `accountIngressHeaders`
    sends the key to every non-loopback API and never to a loopback one.
    `accountUpstreamHeaders` builds the key and `X-Real-IP` for the BFF, the VK
    callback and the server reads (one helper instead of three copies).
  - `src/instrumentation.ts`: `assertPortalConfig` at startup, so a bad
    configuration refuses to serve (`OMOBA portal misconfigured, refusing to serve
    (fail closed)`) instead of failing each account call.
  - `tests/account-ingress.test.mjs`: the RU production configuration, the key
    rules for every contour and market, the trust switch, the shared helper.
  - `tests/ru-topology.e2e.mjs` (`npm run test:ru-topology`): the RU build with the
    production RU settings, the real Account API, a disposable PostgreSQL and a
    Caddy stand-in. README, `.env.example`, `docs/markets.md` and `docs/TESTING.md`.

## Remaining

- **RU Account API binary.** The e2e ran against a global debug build of
  `omoba-account-api` (the only binary on this machine), so VK sign-in success
  was not exercised; the callback, its route and its per-IP limit were. Rerun
  with `OMOBA_MARKET=ru cargo build -p omoba-account-api` and without
  `OMOBA_E2E_API_MARKET=global`.
- **Needs the host (LR-01):** real Caddy with TLS. After deploy, run
  `make release-ru-preflight` (must print `ready: true`) and one real VK sign-in;
  the stand-in models only `header_up X-Real-IP {remote_host}` and the route
  matchers.
- **Owner:** nothing new. If an anti-DDoS proxy is ever put in front of Caddy,
  switch `{remote_host}` to `{client_ip}` with `trusted_proxies` (README note).
